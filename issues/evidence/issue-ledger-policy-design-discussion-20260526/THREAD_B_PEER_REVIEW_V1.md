A states this directly: Git should hold a durable machine-readable ledger sufficient for worker startup, review, merge, and recovery, but not all historical issues, evidence, and local issue detail under one active issues/*.jsonl gate. It identifies that issues/*.jsonl is overloaded as “all issue ledger files,” “current v1 records,” and “complete validation universe,” and says legacy 260519.jsonl causes a full-gate failure while scoped current-v1 validation passes.   THREAD_A_REPLY_V1  A’s proposed active / archive / legacy validation classes are strong. B argued for replay, fsck, snapshots, and archive integrity, but A adds a necessary operational distinction: normal worker startup should not require full-history validation, while release or migration jobs can.   THREAD_A_REPLY_V1  A’s structured evidenceRefs[] proposal is probably the cleanest policy-patch seed in the whole exchange: ref, kind, sha256, sizeBytes, storageTier, retentionClass, sensitivity, and requiredForClose. This directly addresses large evidence, privacy, artifact reachability, and review burden without requiring bulky evidence to live in Git.   THREAD_A_REPLY_V1  A also catches two important workflow semantics that B underweighted: narrowing after partial resolution and split-vs-supersede rules. A says a partially resolved issue can remain open/ready after narrowing, and that same-issue supersession should be used only when worker-facing problem and close criteria remain continuous.   THREAD_A_REPLY_V1  A’s warning that archive technologies can hide evidence is right: LFS, git-annex, artifact stores, and archive branches may preserve blobs while making them unavailable to a worker unless stable refs, hashes, and retrieval expectations are policy-defined.   THREAD_A_REPLY_V1  2. objections to A  A is correct that Git should not be the evidence data plane, but it risks under-specifying the canonical event/replay layer. B’s position was that repo-local issue design should not rely only on mutable issue files; it needs an append-only event stream, generated views, latest-state materialization, snapshots, archive verification, and fsck/replay acceptance tests.   THREAD_B_REPLY_V1  A’s “latest active issue record plus repo policy” invariant is useful but insufficient by itself. A must still say what proves that the latest record was derived correctly: event ordering, duplicate-event idempotence, supersedes resolution, missing-parent detection, hash verification, and replay determinism. The adjacent JSONL + SQLite design supports this shape: JSONL is the append-only audit log, SQLite is only the fast latest-state view, duplicates are ignored, and API reads should not scan JSONL every time.   SPEC  A discusses merge conflicts but does not fully answer B’s concurrency-model objection. Before multi-agent issue mutation is allowed, policy or repo-local design must declare whether issue state is single-writer, multi-writer event stream, or hybrid. Without that, A’s sharding/manifest advice may reduce line conflicts while still permitting semantic lost updates.  A also underweights issue/code publication divergence. B called out that code can publish while issue refs fail, leaving “fixed code / open issue” remote divergence. A’s validation-mode proposal should add a post-push compare or atomic-publication requirement before closure.  A is weaker on approval laundering. A mentions same-revision no-objections and facilitator summary not being a verdict in open questions, but that belongs in the policy patch candidate, not just an unresolved question. B’s objection remains: upload, readback, generated report, discussion reply, or issue-ledger record must not imply approval, merge permission, cleanup permission, or implementation acceptance.   THREAD_B_REPLY_V1  A labels many items as “policy-rule-change candidate.” That is useful for agenda enumeration, but the policy patch should not absorb repo-local HOWTO. B’s boundary should stand: global policy defines invariants; repo-local design chooses paths, storage, tools, manifests, validation commands, and migration mechanics.   THREAD_B_REPLY_V1  3. agenda items to add/remove/rename  Add: “Issue backend and concurrency mode.” This should force a repo to declare single-writer, multi-writer, or hybrid issue mutation semantics before same-issue multi-agent work.  Add: “Evidence state taxonomy and approval boundary.” A has evidence storage; B has evidence-state and approval-laundering concerns. Combine them: raw evidence, candidate summary, adopted policy, rejected, deprecated, hold, and out-of-scope must not be confused with approval.  Add: “Replay, snapshot, fsck, and latest-state proof.” A’s active/latest worker invariant needs a proof path. Latest records should be reproducible from canonical events or clearly marked as authoritative superseding records.  Add: “Publication divergence and post-push verification.” Issue state and code state can diverge when Git publication partially succeeds. This is separate from validation and must be tested.  Rename: “Should issues live inside Git-managed repo paths at all?” → “What issue control plane belongs in Git?” A’s own answer is not “no Git issues”; it is “small control plane in Git, bulky evidence outside Git.” The renamed agenda better matches the conclusion.  Rename: “Does append-only JSONL make repo volume grow too much?” → “What lifecycle bounds append-only ledgers?” The issue is not append-only itself; it is segmentation, snapshotting, compaction, archive restore, and validation class.  Rename: “Should validation always cover all issues/*.jsonl?” → “Which validation mode applies at worker startup, release, migration, and audit?” A’s strongest contribution is multiple gate meanings. The agenda should encode those modes explicitly.  Remove or demote: “Should compression remove the concern?” Compression is a mechanism, not the real question. The real agenda item is archive integrity, restore SLA, worker availability, and whether compression changes semantics. A’s own risk section says compression reduces size but not governance burden. The project has not chosen the issue backend mode: single-writer issue files, multi-writer event streams, or hybrid guarded fields plus append-only evidence/comments.  The canonical source of truth is still ambiguous: latest active issue record, append-only event log, superseding authoritative record, or generated/materialized view.  Active-only validation is necessary for worker usability, but not sufficient for safety. Release, migration, and audit gates must detect broken archives, missing evidence refs, stale supersedes, and hidden obligations.  Structured evidence refs solve naming and metadata, but not restore authority. The project still needs artifact-store credentials policy, cold archive restore SLA, required-vs-optional evidence behavior, and secret/sensitivity handling.  A’s agenda does not fully handle issue/code publish divergence. Closure should require either atomic publication or post-push comparison proving issue state and code state are synchronized.  Approval laundering remains open. Same-revision no-objections, facilitator summaries, generated reports, file uploads, and readbacks must be evidence, not verdicts.  Split-vs-supersede needs test cases. The NO_UNRESOLVED_OBJECTIONS marker bug and the narrowed Project Source issue are good candidates, but policy should specify expected behavior before migration.  Compression and archive remain semantic traps. Compaction must be derived unless explicitly reviewed as an authoritative superseding record; otherwise archive tooling can silently rewrite audit history.  The A-style blind spot remains: “full validation over every historical file” is not safety, but “latest active record only” is not safety either. The policy needs layered validation with explicit meanings, not a single ritual gate.

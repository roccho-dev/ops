POSITION  REVISION_REQUIRED.  The main change I would require is: policy should define invariants, not implementation HOWTOs; repo-local issue design must absorb the storage, concurrency, replay, snapshot, archive, and backend-specific mechanics.  Git-managed issues are acceptable, but only if the design explicitly chooses between single-active-writer issue files and multi-writer issue event streams. The retrieved ticket-vs-Beads evidence shows that ticket-like repo-local files are simpler when there is one active writer per ticket, but they silently lose structured dependency updates under concurrent same-item mutation; Beads/Dolt-style substrates are stronger for relation/independent-field concurrency but still do not provide universal conflict-free behavior.   ticket-vs-beads-aligned-matrix  Large issue/evidence volume does change the repo-local design and should modestly change policy. The policy should require an append-only evidence/issue log, replayability, latest-state materialization, and cold archive integrity. It should not mandate a particular storage engine. The JSONL + SQLite PoC is the clearest supporting pattern: JSONL remains the audit log, SQLite is the fast latest-state view, duplicate event replay is ignored, and API reads must not scan JSONL every time.   SPEC  Compression/archive should not change the meaning of issue state. The snapshot lifecycle documents the right split: current state can be served from memory or latest-state indexes, facts remain in JSONL, snapshots make boot fast, and closed segments before the snapshot boundary can become cold while remaining available for audit/full replay. The runtime-boundary rule is also important: core decides event/reducer/snapshot/segment/cold semantics; runtime adapters decide storage, hashes, compression, and file access.  POLICY_GAPS  No explicit evidence-state taxonomy. Policy should distinguish raw_evidence, candidate_summary, adopted_policy, rejected, deprecated, hold, and out_of_scope. Without that, discussion artifacts and derived summaries can accidentally become normative.  No clear approval boundary. The policy must state that file upload, readback, thread reply, generated report, branch inventory, or issue-ledger record does not authorize merge, push, cleanup, branch deletion, issue closure, or implementation acceptance.  Git-managed issue backend is under-specified. Policy should require each repo to declare its issue-backend mode:  single-writer: one active claim/lease per issue, strict CAS/update check, no same-issue multi-agent writes.  multi-writer: field/relation-level conflict surfacing, replay tests, and explicit merge semantics.  hybrid: append-only comments/evidence are multi-writer; issue status/ownership/deps are guarded by claim/CAS.  Large-volume behavior is not policy-visible enough. Policy should define invariant-level requirements: append-only source of truth, materialized latest view, replay, duplicate idempotence, segmenting, snapshot manifest, hash verification, and full replay audit. It should not say “use SQLite” globally, but it should permit or require a latest-state view once raw-log reads become operationally unsafe.  Archive/compression semantics need a boundary. Policy should say compression is allowed only for closed/cold segments after snapshot boundary and only if hash/manifest/full-replay restore remain valid. It should not let compression become deletion, nor let runtime compression details leak into policy semantics.  Worst-case Git publish failures are not elevated enough. The repo design needs policy-visible invariants for partial issue/code publish divergence, closed-issue resurrection, origin ref deletion/rename, and toolchain drift. The worst-case simulations already call out these exact failure modes for refs/issues/*, stale closed issues, ref deletion/rename, and git-native-issue/awk drift.   urn__spec__worst_case_simulatio…  Policy appears vulnerable to package-detail capture. If v1 embeds package HOWTOs, WebMCP details, ops-cdp-core operational steps, or forge-specific commands as policy, it will overfit. Those belong in package contracts or repo-local runbooks. Policy should retain only authority, provenance, replay, approval, and migration invariants.  REPO_DESIGN_GAPS  Canonical issue state needs an event layer. A repo-local issue design should not rely only on mutable Markdown issue files. Use an append-only event stream as source of truth, then generate Markdown, dashboards, SQLite/latest views, and summaries.  Suggested repo shape:  issues/events/*.jsonl — canonical issue/evidence events.  issues/views/latest.sqlite or generated issues/views/latest/*.json — derived latest-state view, never canonical.  issues/snapshots/manifest.json — snapshot pointer, hash, applied sequence, cold boundary.  issues/snapshots/*.json or compressed runtime output — canonical snapshot payload.  issues/archive/cold/* — compressed closed segments, hash-addressed.  issues/evidence-ledger.jsonl — artifact path/hash/type/readability/caveat/source classification.  issues/generated/*.md — readable reports, indexes, issue pages; generated only.  tools/issue-ledger — append, replay, fsck, snapshot, verify-archive, materialize.  Latest-state reads must not scan all evidence. The JSONL + SQLite PoC already demonstrates tail ingest, duplicate protection, package latest-state tables, and replay into a fresh DB. That pattern should be ported to issue state if evidence volume is expected to grow.   SPEC  Snapshot and cold archive must be first-class. The current design should adopt the snapshot lifecycle boundary: snapshot stores canonical state plus applied sequence, derived indexes are rebuilt, and old logs can be cold only after snapshot boundary.   SNAPSHOT_LIFECYCLE  Compression must live below semantic core. Runtime can decide gzip/zstd/file storage, but repo policy/core must decide what is eligible for cold compaction. This prevents “we compressed it” from becoming “we changed or deleted evidence.”   RUNTIME_BOUNDARY  Concurrency model must be explicit before multi-agent use. If the repo uses ticket-like Markdown/YAML issue files, then same-issue multi-agent writes should be disallowed by policy and tooling. If same-issue parallelism is required, use an event or database-backed substrate with explicit contention behavior.   ticket-vs-beads-aligned-matrix  Git publication needs post-push verification. One push containing code and issue refs is not enough unless the remote is compared after publication. The partial-publish simulation shows the failure: code branch push can succeed while refs/issues/* push fails, leaving fixed code and open issue state diverged.   urn__spec__worst_case_simulatio…  Generated views must be treated as disposable. Markdown issue pages, dashboards, summaries, and review packets are views. They should be rebuildable from events + snapshots + evidence ledger. RISKS  Silent lost update risk. Ticket-like Git files can look safe under one-writer workflows but lose structured updates under concurrent same-item writes.   ticket-vs-beads-aligned-matrix  Issue/code divergence risk. If code refs and issue refs publish separately, a “fixed” code state can coexist with a remote-open issue state.   urn__spec__worst_case_simulatio…  Archive-as-deletion risk. Compression without manifest/hash/replay discipline can become silent evidence loss.  SQLite shadow-truth risk. If any tool mutates SQLite/latest views directly, the append-only event log stops being the source of truth.  A-style overconfidence risk. A-style flows tend to assume the process can classify, route, verify, and archive in one clean path. The blind spot is that misclassification often appears only after contradictory evidence or user challenge. Policy needs explicit self-correction and contradiction capture, not just “review on exception.”  Central-log insufficiency risk. A central log or generated review packet is not enough for large evidence volume. It must be an index into replayable facts, not the fact store.  Same-issue parallelism risk. If multiple agents update one issue, “append comments are safe” does not imply status/deps/claims/closure are safe.  Toolchain drift risk. Git-native issue tooling, shell tools, parsers, hooks, and awk/Git versions can produce local success and CI/restore failure unless pinned and fscked.   urn__spec__worst_case_simulatio…  Policy bloat risk. Putting package-specific runbooks into global policy will make the policy hard to evolve and unsafe to reuse.  Approval laundering risk. Discussion records, project-source readback, generated artifacts, or “review packet created” can be mistaken for approval unless policy forbids that explicitly.
